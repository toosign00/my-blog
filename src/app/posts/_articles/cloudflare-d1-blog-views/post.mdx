블로그를 거의 다 만들고 나서 홈 화면 우측 카드에 넣을 콘텐츠를 고민했습니다. 뭐가 있을까 하다가 마침 떠오른 게 조회수였는데, 포스트 카드에 숫자가 보이면 소소하게 읽을 맛도 날 것 같았습니다.

Vercel Analytics를 이미 붙여뒀지만, 그쪽은 대시보드에서만 확인할 수 있고 페이지나 게시물에 직접 숫자를 노출하려면 직접 집계해서 저장하는 DB가 따로 필요했습니다. Vercel에 배포 중인 Next.js 블로그라 Supabase가 설정은 더 간단하지만, 도메인, S3 스토리지, 이메일 인증까지 이미 Cloudflare로 관리하고 있던 터라 DB도 같은 생태계 안에서 해결하고 싶었습니다.

---

## Cloudflare D1이 뭔가요?

D1은 Cloudflare가 제공하는 서버리스 SQLite 데이터베이스입니다. Cloudflare Workers와 함께 쓰도록 설계됐지만, REST API도 제공하기 때문에 Next.js 같은 외부 환경에서도 HTTP 요청으로 쿼리를 날릴 수 있습니다.

이 블로그는 Vercel에 배포되어 있어 Workers 바인딩을 쓸 수 없는 상황이었는데, REST API 덕분에 문제없이 연결할 수 있었습니다. 선택한 이유는 단순했습니다. 무료 플랜으로 충분하고, SQL을 그대로 쓸 수 있고, 별도 인프라 관리가 필요 없었습니다.

---

## 테이블 구조

조회수처럼 화면에 숫자만 보여주면 되는 기능이라, 방문 이벤트를 전부 로그로 쌓기보다는 **보여줄 숫자는 숫자 테이블에 저장하고, 중복 방지에 필요한 최근 방문 기록만 따로 짧게 보관하는 구조**로 잡았습니다.

이렇게 하면 조회할 때마다 전체 행을 세지 않아도 되고, IP 같은 원본 방문 기록을 오래 들고 있을 필요도 없습니다.

```sql
CREATE TABLE page_view_counts (
  pathname   TEXT PRIMARY KEY,
  total      INTEGER NOT NULL DEFAULT 0,
  updated_at INTEGER NOT NULL
);

CREATE TABLE daily_site_visit_counts (
  visit_date TEXT PRIMARY KEY,
  total      INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE recent_page_viewers (
  visitor_key TEXT NOT NULL,
  pathname    TEXT NOT NULL,
  visited_at  INTEGER NOT NULL,
  PRIMARY KEY (visitor_key, pathname)
);

CREATE TABLE recent_site_visitors (
  visitor_key TEXT PRIMARY KEY,
  visited_at  INTEGER NOT NULL
);
```

`page_view_counts`는 게시물별 조회수 숫자를 저장합니다. `/posts/filmlog-01` 같은 경로가 하나의 row가 되고, 방문이 인정될 때 `total`만 1씩 올립니다.

홈 화면의 `Total Visits`는 `daily_site_visit_counts`에서 계산합니다. 페이지뷰 전체 합이 아니라, 같은 방문자가 여러 글을 읽어도 30분 안에는 한 번만 올라가는 사이트 방문수에 가깝습니다.

`recent_page_viewers`와 `recent_site_visitors`는 중복 방지용입니다. 영구 분석 로그가 아니라 "이 방문자가 30분 안에 같은 페이지를 봤는지"만 판단하기 위한 임시 기록입니다.

## D1에 쿼리 날리기

Cloudflare REST API를 직접 호출하는 유틸 함수를 하나 만들었습니다.

```ts
export async function queryD1<T = Record<string, unknown>>(
  sql: string,
  params: (string | number)[] = []
): Promise<T[]> {
  const accountId = process.env.CLOUDFLARE_ACCOUNT_ID;
  const databaseId = process.env.CLOUDFLARE_D1_DATABASE_ID;
  const apiToken = process.env.CLOUDFLARE_API_TOKEN;

  const res = await fetch(
    `https://api.cloudflare.com/client/v4/accounts/${accountId}/d1/database/${databaseId}/query`,
    {
      method: 'POST',
      cache: 'no-store',
      headers: {
        Authorization: `Bearer ${apiToken}`,
        'Content-Type': 'application/json',
      },
      body: JSON.stringify({ sql, params }),
    }
  );

  const data = await res.json();
  return data.result?.[0]?.results ?? [];
}
```

환경변수 3개(`CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_D1_DATABASE_ID`, `CLOUDFLARE_API_TOKEN`)만 있으면 어디서든 SQL을 실행할 수 있습니다.

## 조회수 기록 API

Next.js Route Handler로 `GET /api/views`(조회)와 `POST /api/views`(기록) 두 가지를 만들었습니다.

새로고침할 때마다 카운트가 올라가면 안 되기 때문에, 익명 방문자 쿠키를 하나 둡니다. 쿠키가 없으면 `crypto.randomUUID()`로 만들고, 서버에서는 이 값을 `visitor:<uuid>` 형태의 키로 사용합니다.

```ts
const INTERVAL_MS = 30 * 60 * 1000;
const VISITOR_COOKIE = 'views_visitor_id';

const visitorId = request.cookies.get(VISITOR_COOKIE)?.value ?? crypto.randomUUID();
const visitorKey = `visitor:${visitorId}`;
```

로컬호스트 요청은 카운트하지 않습니다. 개발 중에 새로고침한 기록이 운영 조회수에 섞이지 않게 하기 위해서입니다.

```ts
const ip = getClientIp(request);

if (ip === '127.0.0.1' || ip === '::1') {
  return NextResponse.json({ ok: true, counted: false });
}
```

중복 체크는 최근 방문자 테이블을 봅니다. 같은 방문자가 30분 안에 같은 페이지를 다시 보면 숫자를 올리지 않습니다.

```ts
const cutoff = Math.floor((Date.now() - INTERVAL_MS) / 1000);

const recent = await queryD1<{ cnt: number }>(
  `SELECT COUNT(*) as cnt
   FROM recent_page_viewers
   WHERE visitor_key = ? AND pathname = ? AND visited_at >= ?`,
  [visitorKey, pathname, cutoff]
);
```

중복이 아니면 `page_view_counts`의 숫자를 1 올립니다. 경로가 처음 들어오면 row를 만들고, 이미 있으면 `total`만 증가시킵니다.

```ts
await queryD1(
  `INSERT INTO page_view_counts (pathname, total, updated_at)
   VALUES (?, 1, ?)
   ON CONFLICT(pathname) DO UPDATE SET
     total = total + 1,
     updated_at = excluded.updated_at`,
  [pathname, now]
);
```

그리고 같은 방문자가 30분 안에 다시 들어왔는지 판단할 수 있게 최근 방문 기록을 갱신합니다.

```ts
await queryD1(
  `INSERT INTO recent_page_viewers (visitor_key, pathname, visited_at)
   VALUES (?, ?, ?)
   ON CONFLICT(visitor_key, pathname) DO UPDATE SET visited_at = excluded.visited_at`,
  [visitorKey, pathname, now]
);
```

사이트 방문수도 비슷하게 처리합니다. 다만 페이지별 조회수가 아니라 사이트 전체 방문수라서, `daily_site_visit_counts`의 오늘 날짜 row를 1 올립니다.

```ts
await queryD1(
  `INSERT INTO daily_site_visit_counts (visit_date, total)
   VALUES (?, 1)
   ON CONFLICT(visit_date) DO UPDATE SET total = total + 1`,
  [today]
);
```

## 조회수 / 방문수 계산

게시물 조회수는 더 이상 행을 세지 않습니다. 이미 숫자로 저장되어 있으니 해당 경로의 row 하나만 읽으면 됩니다.

```sql
SELECT 0 as today, total
FROM page_view_counts
WHERE pathname = ?
```

홈 화면에 보여주는 `Today`와 `Total Visits`는 날짜별 사이트 방문수 테이블에서 계산합니다.

```sql
SELECT
  COALESCE(SUM(CASE WHEN visit_date = ? THEN total ELSE 0 END), 0) AS today,
  COALESCE(SUM(total), 0) AS total
FROM daily_site_visit_counts
```

페이지뷰와 방문수를 분리한 이유는 홈 화면 숫자가 과하게 올라가는 문제 때문이었습니다. 한 사람이 글 3개를 읽고 홈으로 돌아오면 페이지뷰는 4가 맞지만, 사이트 방문수까지 4가 되는 건 어색했습니다. 그래서 게시물별 조회수는 페이지 단위로 올리고, `Total Visits`는 30분 안에 한 번만 올라가도록 분리했습니다.

## 서버 렌더링에서 조회수 분리하기

처음에는 서버 컴포넌트에서 조회수를 가져왔는데, 다른 문제가 있었습니다. 조회수 때문에 페이지 HTML 응답이 D1 REST API를 기다려야 했습니다.

조회수는 글 본문보다 덜 중요한 정보라서, 페이지는 먼저 정적으로 보여주고 조회수만 클라이언트에서 따로 가져오도록 바꿨습니다. 숫자가 오기 전에는 `- views`를 보여줍니다.

```tsx
export const PostViews = ({ slug }: PostViewsProps) => {
  const { data } = useViewsQuery(`/posts/${slug}`);
  return (
    <span className='ml-4 tabular-nums'>{data ? data.total.toLocaleString() : '-'} views</span>
  );
};
```

## TanStack Query로 실시간 반영

클라이언트에서 조회수를 가져오게 바꾸면서 TanStack Query를 붙였습니다. 페이지가 먼저 뜨고, 조회수 API가 최신 숫자를 가져오면 화면이 갱신됩니다.

조회수는 오래된 캐시가 보이면 안 되기 때문에 API 응답과 fetch 모두 `no-store`로 맞췄습니다. `POST /api/views`가 끝나면 해당 경로의 조회수 쿼리와 사이트 방문수 쿼리를 invalidate합니다.

```ts
const mutation = useMutation({
  mutationFn: () => postViews(pathname),
  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: ['views', pathname] });
    queryClient.invalidateQueries({ queryKey: ['views', '__site__'] });
  },
});
```

이렇게 하면 내가 방문한 순간 조회수가 올라가는 모습을 바로 확인할 수 있습니다.

## 마치며

D1은 간단한 집계 용도로 쓰기에 딱 맞습니다. Workers 없이 REST API만으로도 충분히 연결할 수 있고, 무료 플랜에서도 개인 블로그 트래픽 정도는 여유롭게 처리됩니다.

조회수처럼 가벼운 기능에 별도 DB 서비스를 붙이는 게 과하다고 느껴질 수 있는데, D1은 설정 비용이 거의 없어서 부담이 없었습니다.
